# Pouch — 빠른 압축/해제 프로그램

Rust로 만든 멀티코어 압축 프로그램. 목표는 반디집보다 빠른 압축·해제.

> 프로그램 이름은 **Pouch**, 자체 압축 형식의 확장자는 **`.bzx`** 입니다.

| | 만들기 | 풀기 |
|---|:---:|:---:|
| **bzx** (Pouch 자체 형식 — 가장 빠르고 작음) | ✅ | ✅ |
| **zip** (어디서나 열림) | ✅ 멀티코어 | ✅ |
| 7z | | ✅ |
| tar, tar.gz, tar.bz2, tar.xz, tar.zst | | ✅ |
| 단일 .gz / .bz2 / .xz / .zst | | ✅ |

형식은 확장자가 아니라 파일 앞부분(매직 넘버)으로 알아내서, 확장자가 틀려도 열립니다.
한글 이름이 CP949로 들어 있는 zip(윈도우 기본 압축 기능으로 만든 것 등)도 이름이 깨지지 않습니다.

## 설치 (Windows, 처음 한 번만)

1. https://rustup.rs 에서 `rustup-init.exe`를 받아 실행합니다.
   설치 중 **Visual Studio C++ Build Tools**를 설치하라고 하면 설치합니다.
   zstd 라이브러리가 C로 되어 있어서 필요합니다.
2. 새 터미널(PowerShell)을 열고 `cargo --version`이 나오는지 확인합니다.

## 빌드 & 실행

```powershell
cd D:\GitHub\CompressionProgram
cargo build --release     # 처음엔 몇 분 걸립니다
.\target\release\pouch-gui.exe   # 창 프로그램 실행
cargo test --release      # 테스트 (28개)
```

`target\release` 폴더에 실행 파일 두 개가 생깁니다.

- `pouch-gui.exe` — 창 프로그램 (이 exe 하나만 복사해서 써도 됩니다)
- `pouch.exe` — 명령줄 버전 (스크립트·벤치마크용)

> 끌어다 놓기가 안 되면: 관리자 권한으로 실행 중인지 확인하세요. 윈도우는 관리자 권한 창에
> 일반 탐색기에서 끌어다 놓는 것을 막습니다. 탐색기에서 `pouch-gui.exe`를 더블클릭해 실행하면 됩니다.

## 창 프로그램 사용법

- **압축:** 파일이나 폴더를 창에 끌어다 놓기 (또는 "파일 추가"/"폴더 추가") → **형식**(bzx / zip)과 압축 수준 고르기 → **압축 시작**
- **풀기:** 압축 파일(bzx, zip, 7z, tar…)을 창에 끌어다 놓기 (또는 "압축 파일 열기") → 안의 목록 확인 → **압축 풀기**
- 진행률·속도·남은 시간이 아래에 표시되고, 언제든 **취소**할 수 있습니다.
- 끝나면 **폴더 열기**로 결과를 탐색기에서 바로 볼 수 있습니다.
- 풀 때 **같은 이름**이 이미 있으면 고를 수 있습니다:
  - **번호 붙이기** (기본): `사진` → `사진 (1)`, `메모.txt` → `메모 (1).txt`
  - **덮어쓰기**: 기존 파일을 새 것으로 바꿉니다 (폴더는 합쳐짐)
  - **멈추기**: 겹치는 파일이 있으면 멈춥니다
- **⚙ 설정 → ".bzx 파일에 아이콘 붙이고 Pouch로 열기"** 를 한 번 누르면 `.bzx` 파일에 Pouch 아이콘이 보이고, 더블클릭하면 Pouch로 열립니다. (관리자 권한 필요 없음, 같은 메뉴에서 해제 가능)

## 명령줄 사용법

```powershell
$pouch = ".\target\release\pouch.exe"

# 압축 — 파일이든 폴더든 OK (기본: bzx 형식, 레벨 3, CPU 코어 전부 사용)
& $pouch c D:\사진                     # → D:\사진.bzx
& $pouch c D:\사진 --format zip        # → D:\사진.zip (어디서나 열림)
& $pouch c D:\사진 -o 보낼거.zip        # -o 확장자가 .zip이면 zip으로
& $pouch c 큰파일.iso -l 9 -t 8          # 레벨·스레드 지정

# 풀기 — 형식 자동 감지, 기본은 압축 파일이 있는 폴더에 풀기 ("여기에 풀기")
& $pouch x D:\사진.bzx
& $pouch x 받은파일.zip -o E:\복원
& $pouch x 백업.tar.gz                # 7z, tar.xz, tar.zst … 모두 같은 방법
& $pouch x D:\사진.bzx -f             # 덮어쓰기 (= --on-conflict overwrite)
& $pouch x D:\사진.bzx --on-conflict stop   # 겹치면 멈춤

& $pouch l 받은파일.zip   # 목록 (zip·7z는 목차만 읽어서 즉시)
& $pouch t D:\사진.bzx   # 풀지 않고 손상 검사
& $pouch info D:\사진.bzx
```

## 어떻게 빠른가

### bzx 형식(v3): 블록 병렬 압축·해제

```text
            ┌─ 작업자 1 ─┐
메인 ──4MB 블록─┼─ 작업자 2 ─┼──결과──▶ 출력 스레드(순서 맞추기) ──▶ 파일
            └─ 작업자 N ─┘
```

- 파일 내용을 하나의 스트림으로 이어서(솔리드) **4MB 블록**으로 자르고, 블록마다 독립적으로 zstd 압축합니다.
- 블록이 서로 독립적이라 **해제도 CPU 코어 수만큼 동시에** 됩니다. (v2는 해제가 한 스레드뿐이었음)
- 파일 끝의 **블록 인덱스**(블록별 압축/원본 크기)로 블록 위치를 바로 압니다.
- 사진·영상처럼 **이미 압축된 블록은 감지해서 그대로 저장**합니다 (바이트 엔트로피 + 64KB 시험 압축).
- 스레드 수와 상관없이 **항상 같은 결과 파일**이 나옵니다 (테스트로 확인).
- 예전 v2 파일도 그대로 열립니다.

### 풀 때: 작은 파일 병렬 쓰기

작은 파일이 수천 개인 폴더는 압축 해제보다 "파일 만들기" 자체가 병목입니다 (특히 윈도우는 백신 검사까지 기다림).
1MB 이하 파일은 쓰기 스레드 풀에 넘겨서 동시에 만듭니다. 같은 폴더의 파일은 같은 스레드로 보내서 폴더 잠금 경쟁을 피합니다.

### zip 만들기: 멀티코어 Deflate (직접 만든 zip 작성기)

- 파일을 **1MB 조각**으로 잘라 여러 스레드가 동시에 Deflate 압축합니다 (pigz와 같은 방식).
- 조각마다 앞 조각의 마지막 32KB를 **사전(dictionary)** 으로 넣어 압축률 손해를 거의 없앱니다.
- 마지막이 아닌 조각은 바이트 경계에서 끝나게(sync flush) 만들어, 이어 붙이면 하나의 올바른 Deflate 스트림이 됩니다.
- zip 구조(로컬 헤더, 중앙 디렉터리, **zip64**)를 APPNOTE 명세대로 직접 씁니다. 이름은 UTF-8 플래그, 수정 시각은 확장 타임스탬프까지 기록합니다.
- Python `zipfile`, Info-ZIP `unzip -t`로 검증했습니다 (zip64 포함).

## 벤치마크

클라우드 개발 환경(**CPU 2코어**)에서 잰 값입니다. 각 3번 재서 중간값, 측정 사이마다 디스크 쓰기를 비웠습니다.
코어가 많은 PC일수록 Pouch·zip 만들기의 차이가 더 벌어집니다. **내 PC에서 반디집과 비교하려면 아래 스크립트를 쓰세요.**

| 데이터 | 방식 | 압축 | 해제 | 크기 |
|---|---|---:|---:|---:|
| 큰 파일 1개 (381MB) | v2 (이전 버전) | 0.86초 | 0.57초 | 52.6MB |
| | **bzx v3** | 0.90초 | **0.33초** | 53.5MB |
| | **Pouch → zip** | **2.58초** | 0.62초 | 59.8MB |
| | Info-ZIP zip -6 (1스레드) | 9.74초 | 2.47초 | 59.8MB |
| 사진·영상 16개 (382MB, 압축 불가) | v2 (이전 버전) | 0.83초 | 0.38초 | 400.0MB |
| | **bzx v3** | 0.63초 | 0.34초 | 400.0MB |
| | **Pouch → zip** | **0.61초** | 0.49초 | 400.0MB |
| | Info-ZIP zip -6 | 13.79초 | 2.96초 | 400.1MB |
| 소스코드 23,502개 (551MB) | v2 (이전 버전) | 1.06초 | — | 61.6MB |
| | **bzx v3** | 1.19초 | — | 62.7MB |
| | **Pouch → zip** | **5.05초** | — | 84.6MB |
| | Info-ZIP zip -6 | 11.71초 | — | 85.4MB |

- 작은 파일 수만 개를 **푸는** 시간은 이 환경의 디스크 상태에 따라 같은 프로그램도 2~13초로 흔들려서 표에서 뺐습니다.
  번갈아 5번 잰 결과로는 v3가 대체로 30% 안팎 빨랐지만, 실제 PC에서 다시 재야 정확합니다.
- 블록을 독립적으로 압축하는 대가로 bzx 크기가 1~2% 커졌습니다 (블록 경계를 넘는 중복은 못 찾음).

### 내 PC에서 반디집과 비교하기

```powershell
cargo build --release
powershell -ExecutionPolicy Bypass -File tools\bench.ps1 -Target "D:\비교할 폴더"
```

반디집의 명령줄 도구(`bz.exe`)를 자동으로 찾아서 **Pouch(.bzx) / Pouch(.zip) / 반디집(.zip)** 의 압축·해제 시간과 크기를 비교하고,
**Pouch가 만든 zip을 반디집이 정상적으로 푸는지**까지 확인합니다. 결과는 `bench-result.md`로 저장되어 README에 그대로 붙여 넣을 수 있습니다.

|---|---|
| `src/lib.rs` | 공통 — 진행률·취소(`Control`), 압축할 항목 모으기, 형식별로 나눠 보내기 |
| `src/format.rs` | `.bzx` 형식 정의 — 헤더(v3), 항목 레코드, 안전한 경로 검사, 외부 경로 정리 |
| `src/block.rs` | **블록 병렬 압축/해제** — 작업 스레드, 순서 맞추기, 압축 불가 블록 감지, 블록 인덱스 |
| `src/native.rs` | `.bzx` 만들기·풀기 (v3 쓰기, v2·v3 읽기) |
| `src/zipwrite.rs` | **zip 작성기** — 조각 병렬 Deflate, zip64, 확장 타임스탬프 |
| `src/foreign.rs` | 다른 형식 풀기 — 형식 감지, zip(CP949 이름), 7z, tar 계열, 단일 압축 파일 |
| `src/sink.rs` | 풀어서 쓰기 — 이름 충돌 처리, 작은 파일 병렬 쓰기, 수정 시각 복원 |
| `src/main.rs` | 명령줄 인터페이스 (clap) |
| `src/bin/pouch-gui.rs` | 창 프로그램 (egui) — 끌어다 놓기, 형식 선택, 진행률, 취소, 목록 미리보기 |
| `src/assoc.rs` | Windows 파일 연결 — 레지스트리(HKCU) 등록/해제, 탐색기 아이콘 새로 고침 |
| `build.rs`, `assets/` | exe에 아이콘 넣기, 아이콘 원본(SVG)과 .ico |
| `tests/roundtrip.rs` | 기본 왕복, 덮어쓰기 방지, 손상 감지, Zip Slip, 취소, 이름 충돌 |
| `tests/formats.rs` | v3 병렬 블록, 스레드 수와 무관한 결과, v2 호환, zip 왕복·CP949·결정성, tar 계열, 7z, 경로 공격 |
| `tools/bench.ps1` | 반디집과 속도·크기 비교 스크립트 (Windows) |

## 안전장치

- bzx 형식은 파일마다 CRC32를 저장해 풀 때 검사합니다. zip·7z·gz 등은 각 형식의 체크섬으로 검사합니다.
- `../` 같은 경로가 든 악성 압축 파일은 거부합니다 (Zip Slip 방어). tar의 절대 경로(`/etc/…`)는 상대 경로로 바꿔 풉니다.
- 윈도우에서 쓸 수 없는 파일 이름 문자(`: * ? " < > |`)는 `_`로 바꿔 풉니다.
- 같은 이름이 있으면 기본적으로 번호를 붙여 새 이름으로 풀어서, 기존 파일을 건드리지 않습니다.
- 손상·악성 파일이 터무니없는 블록 크기로 메모리를 잡아먹지 못하게 상한을 둡니다.
- 압축 중 취소·오류가 나면 만들던 파일을 지웁니다. 압축 대상 폴더 안에 결과 파일을 만들어도 자기 자신은 건너뜁니다.
